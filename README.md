## 1. はじめに — なぜ今、仕様駆動開発か

AI コーディングエージェントの登場で、コードを「書く」コスト自体は劇的に下がりました。一方で、チャットで思いつくままに指示を重ねる開発スタイル（いわゆる **vibe coding**）には、規模が大きくなると必ず現れる失敗モードがあります。

- **意図からのドリフト**: エージェントはもっともらしいコードを出し続けるが、セッションを重ねるうちに当初の意図から少しずつずれていく
- **コンテキストの消失**: 「何を作りたいか」がチャットログにしか存在せず、セッションが終わると消える。次のセッション、次の担当者、次のエージェントに引き継げない
- **レビュー不能**: 一度に大量のコードが生成され、レビュアーは「この変更は何を意図したものか」を差分から逆算するしかない

**仕様駆動開発（Spec-Driven Development, SDD）** は、この問題への応答として 2025 年に登場した方法論です。コードを生成させる前に「何を・なぜ作るのか」を構造化されたドキュメント（仕様）として確定させ、そこから計画・タスク・実装を段階的に導出します。2025 年 9 月に GitHub が **Spec-kit** をオープンソースで公開したのを皮切りに、AWS Kiro、Tessl、OpenSpec など、2026 年には主要な AI 開発ツールが何らかの形で SDD を取り込むまでに一般化しました。

一言でいえば SDD とは、**「プロンプトを使い捨てるのをやめて、仕様という永続的な成果物に昇格させる」** 方法論です。

## 2. 仕様駆動開発が解決する課題

### 2.1 プロンプトの使い捨て問題

従来の AI コーディングでは、丁寧に書いたプロンプトも一度使えば消えます。SDD では意図が `specs/` 配下のファイルとしてリポジトリにコミットされ、バージョン管理・レビュー・再利用の対象になります。**「何を作るか」がコードと同じ第一級の成果物になる**ことが本質です。

### 2.2 意図とコードの乖離（パワーインバージョン）

Spec-kit 公式の方法論ドキュメント（spec-driven.md）は、SDD を「力関係の逆転（power inversion）」と表現しています。従来、要求文書は実装のための足場であり、コードが完成すれば古びて捨てられるものでした。SDD ではこれを逆転させ、**仕様が実装を生成する源泉**になります。仕様と実装のギャップは「頑張って同期する」ものではなく、実装が仕様から生まれることで構造的に小さく保たれます。

### 2.3 レビューの焦点を「What」に移す

生成コードのレビューは苦痛ですが、仕様のレビューは人間が得意とする作業です。SDD ではレビューの主戦場を「このコードは正しいか」から「**この仕様は正しいか**」に前倒しします。受け入れ基準が明文化されているため、実装レビューも「仕様を満たすか」という判定可能な問いになります。

### 2.4 暗黙知のチーム共有

「このプロジェクトではテストを先に書く」「外部ライブラリは極力使わない」といったチームの流儀は、通常は口頭やレビュー指摘で伝わる暗黙知です。Spec-kit ではこれを **constitution（憲章）** として明文化し、エージェントがすべてのフェーズで参照する制約にします。人間の新メンバーへのオンボーディング資料としても機能します。

## 3. Spec-kit 最新版の概要

Spec-kit は GitHub が公開する SDD のツールキットで、`specify` CLI と、エージェントに読み込ませるコマンド・テンプレート群から構成されます。**リリースサイクルが非常に速く**、2026 年 7 月時点の最新は v0.12.9（2026-07-09 リリース）です。GitHub Copilot、Claude Code、Gemini CLI、Cursor など **30 以上のエージェント**に対応しています。

導入はおおむね次の 2 コマンドです（詳細は[公式クイックスタート](https://github.github.com/spec-kit/quickstart.html)を参照）。

```bash
uv tool install specify-cli --from git+https://github.com/github/spec-kit.git
specify init <プロジェクト名> --integration claude   # 使用エージェントを --integration で指定
```

### 3.1 ワークフローと成果物

初期化するとエージェントに `/speckit.*` 系のスラッシュコマンドが追加されます。基本の流れは次の通りで、各フェーズが 1 つの成果物を生みます。

| フェーズ | コマンド | 成果物 | 内容 |
|---|---|---|---|
| 0. 憲章 | `/speckit.constitution` | `.specify/memory/constitution.md` | プロジェクト不変の原則（品質基準、技術方針、テスト規律） |
| 1. 仕様化 | `/speckit.specify` | `specs/NNN-機能名/spec.md` | ユーザーストーリー・受け入れ基準。**What と Why のみ、技術には触れない** |
| 2. 明確化 | `/speckit.clarify` | spec.md への追記 | 仕様の曖昧箇所をエージェントが質問し、対話で潰す（plan 前に推奨） |
| 3. 計画 | `/speckit.plan` | `plan.md` ほか | 技術選定・アーキテクチャ・データモデル。**How を担当** |
| 4. タスク分解 | `/speckit.tasks` | `tasks.md` | 実装可能な粒度のタスクリスト（並列実行可能性の分析付き） |
| 5. 整合性検証 | `/speckit.analyze` | レポート | spec / plan / tasks 間の矛盾・カバレッジ漏れを検出 |
| 6. 実装 | `/speckit.implement` | コード | タスクを順に実行 |

補助として、品質観点のチェックリストを生成する `/speckit.checklist` があります。

### 3.2 ディレクトリ構造のモデル

```
.specify/
  memory/constitution.md   # 憲章（全フェーズが参照する不変の制約）
  templates/               # spec / plan / tasks のテンプレート
  scripts/                 # 自動化スクリプト
specs/
  001-user-auth/           # 機能ブランチと 1:1 対応
    spec.md  plan.md  tasks.md  ...
```

ポイントは **「機能ブランチ = 仕様ディレクトリ」** というモデルです。`/speckit.specify` を実行すると番号付きの機能ブランチと `specs/` 配下のディレクトリが同時に作られ、仕様の変更履歴がコードと同じ Git のフローに乗ります。

### 3.3 SDD の哲学: 仕様と計画の分離

Spec-kit の設計で最も重要なのは、**仕様（spec.md）と実装計画（plan.md）を意図的に別ファイルに分けている**ことです。仕様はビジネス意図（ユーザーストーリー、受け入れ基準）だけを持ち、技術選定は一切書きません。技術は計画側に隔離されるため、「React を Vue に変える」ような技術変更で仕様は 1 行も変わらず、同じ仕様から複数の実装案を並行検討することもできます。この分離が後述する「仕様の粒度」の議論の土台になります。

## 4. 使用するときの注意点

### 4.1 破壊的変更が多い — 古い記事を信用しない

Spec-kit は数日〜数週間単位でリリースされ、**破壊的変更を躊躇しません**。代表例が v0.10.0（2026 年 6 月）で、CLI の `--ai` / `--ai-commands-dir` / `--ai-skills` フラグが削除され、`--integration <key>` / `--integration-options` に置き換えられました。つまり **2026 年 6 月以前に書かれた解説記事・動画のコマンドはそのままでは動きません**。

- 一次情報は常に[公式リポジトリ](https://github.com/github/spec-kit)と[公式ドキュメント](https://github.github.com/spec-kit/)に取る
- バージョン管理には v0.10 以降で入った `specify self check` / `specify self upgrade` を使う
- チーム内でバージョンを固定したい場合は `--from git+...@vX.Y.Z` でタグを指定してインストールする

### 4.2 小さいタスクには過剰（トークンと時間のコスト）

Spec-kit の強みは要件の明確化と体系的なタスク分割にあるため、**要件数が多く実装規模が大きいタスクほど効きます**。逆に、数行のバグ修正や仕様が自明な小変更にフルワークフローを回すと、トークン消費と待ち時間だけが膨らみます。「この変更に仕様書を書く価値があるか」を最初に自問してください（判断基準は §5 参照）。

### 4.3 AI は過剰設計する — 単純さを憲章で強制する

エージェントに設計を委ねると、不要な抽象レイヤーや汎用化を盛り込む傾向があります。対策は上流に置くのが効果的です。

- constitution に「YAGNI」「実証されるまで抽象化しない」など**単純さを求める原則**を明記する
- `/speckit.clarify` の段階でスコープ外事項（out of scope）を明示的に確定させる
- plan のレビュー時に「この要件に本当にこの構造が必要か」を人間が問う

### 4.4 人間がゲートすべき観点を決めておく

SDD はプロセスを自動化しますが、**判断の責任は移動しません**。特に次の観点はエージェントの出力を鵜呑みにせず、人間が意識的にレビュー・ゲート化すべきポイントです。

- **要求の妥当性**: そもそも正しい問題を解いているか（仕様が流暢に書けていることと、正しいことは別）
- **セキュリティ・パフォーマンス要件**: 仕様に書かれなければ考慮されない
- **SLO/SLA・運用要件**: 障害時の振る舞い、データ保持、コンプライアンス
- **可観測性**: ログ・メトリクス・トレースの設計

### 4.5 constitution の初期品質が全体を左右する

constitution は全フェーズの判断基準として参照されるため、ここが曖昧だと下流のすべてがぶれます。最初の 1 機能を流す前に、チームでレビューして合意した constitution を用意することが、Spec-kit 導入の実質的な最重要タスクです。

### 4.6 ブラウンフィールド・モノレポでの制約

Spec-kit は「機能ブランチ = 仕様ディレクトリ」モデルを前提とするため、次の環境では工夫が要ります。

- **既存の大規模コードベース**: 既存コードの現状仕様は自動では得られない。まず対象領域の現状を要約したコンテキストを constitution や spec に与える必要がある
- **モノレポ**: `specs/` とサブプロジェクトの対応関係を運用ルールで補う必要がある。なお git 連携は現在オプトイン（`specify extension add git`）になっており、ブランチ自動作成を無効にしたまま使うこともできる

## 5. 向いている人・プロジェクト / 向いていないケース

### 向いているケース

| ケース | 理由 |
|---|---|
| 0→1 のグリーンフィールド開発 | 仕様→計画→実装の流れが最も素直に機能する。公式も第一のユースケースに挙げる |
| 要件が流動的なプロジェクト | 仕様を直して再生成する回転が、手でコードを直し続けるより速い |
| 複数の実装アプローチを比較したい | 同じ仕様から別技術スタックの plan を並行して作れる（仕様と計画の分離の恩恵） |
| チームでの合意形成が必要な開発 | 仕様がレビュー可能な成果物になり、PM・レビュアーと同じものを見て議論できる |
| テストが常に回る環境 | 受け入れ基準→テスト→実装の検証ループが機能し、SDD の価値が最大化される |

### 向いていないケース

- **数行のバグ修正・自明な小変更**: 仕様を書くコストが実装コストを上回る
- **探索的プロトタイピング**: 「作りながら何を作るか発見する」フェーズでは、先に仕様を固定すること自体が邪魔になる。捨てる前提のスパイクは vibe coding で行い、本実装に入る段階で SDD に切り替えるのが現実的
- **仕様を言語化する意思のないチーム**: SDD はツールではなく規律。仕様レビューをスキップして `/speckit.implement` に直行するなら、それはワークフローが重い vibe coding にすぎない

### 向いている「人」

- 実装前に要求を言語化する習慣がある人（設計ドキュメントを書く文化に馴染んだ人はそのまま強みになる）
- レビュー文化が根付いているチーム。SDD はレビュー対象をコードから仕様に前倒しする方法論なので、レビューが形骸化しているチームでは効果が出にくい
- 逆に「文書化は苦手だが対話は得意」な人にも入口がある: `/speckit.specify` と `/speckit.clarify` は対話から仕様を構造化してくれるため、白紙に仕様書を書くより敷居が低い

## 6. 仕様のメンテナンス — ベストプラクティス

### 6.1 中心課題は「仕様ドリフト」

仕様が古びる問題は SDD 固有ではなく、ソフトウェア工学の古典的課題です。ウォーターフォール時代から「スプリント 3 で設計書は現実と乖離し、リリース 2 で要求仕様書は製品と一致しなくなる」と言われてきました。**問題は仕様がないことではなく、仕様がドリフトすること**です。SDD はこれに「仕様からコードを生成するので、仕様を直すことが開発行為そのものになる」という構造で答えますが、それでも運用の規律がなければドリフトは起きます。

### 6.2 3 段階の厳格度 — どこを目指すか

2026 年時点の業界では、仕様とコードの関係を 3 段階で整理するのが一般的です（Martin Fowler サイトの分析などで使われる枠組み）。

| レベル | 仕様の扱い | 特徴 |
|---|---|---|
| **spec-first** | 初回生成の種。以後のドリフトは許容 | 導入が最も軽い。仕様は「開発開始時のスナップショット」になる |
| **spec-anchored** | 生きたドキュメントとして維持 | 振る舞いを変えるときは仕様を先に直す。仕様と実装を同一 PR でレビュー |
| **spec-as-source** | 仕様が第一級の成果物、コードは派生物 | コードを直接編集しない世界観（Tessl などが志向）。まだ実験段階 |

Spec-kit は素のままでは spec-first に近く、運用次第で spec-anchored に引き上げられます。**現実解としての推奨は spec-anchored** です。spec-as-source は現状のツール成熟度では賭けが大きすぎ、spec-first は「立派な初期ドキュメントが腐っていく」従来の失敗を繰り返します。

### 6.3 spec-anchored を実現する運用ルール

1. **振る舞いの変更は仕様から**: 意図した振る舞いが変わるときは、まず `specs/` の spec.md を直し、そこから plan / tasks / 実装を更新する。コードだけ直して仕様を後追いさせない
2. **仕様と実装を同一 PR に**: 仕様の差分と実装の差分を同じ PR でレビューすることで、乖離がレビューで機械的に見つかる状態を作る
3. **`/speckit.analyze` を CI 的に使う**: spec / plan / tasks の整合性検証を、実装前だけでなく変更のたびに回す
4. **受け入れ基準をテストに接続する**: 仕様の受け入れ基準がテストコードに対応していれば、「仕様と実装の乖離」が「テストの失敗」として現れる。これが最も強いドリフト検出器
5. **ツール更新と成果物の進化を分離する**: Spec-kit 本体のアップグレード（テンプレートやコマンドの変化）と、自分たちの仕様の変更を同じコミットに混ぜない（公式アップグレードガイドの推奨）

### 6.4 割り切り: すべての仕様を永遠に生かさなくてよい

すべての機能仕様を未来永劫メンテナンスするのは非現実的です。実務的な割り切りとして、次の 2 層に分けて考えることを推奨します。

- **生き続けるもの**: constitution（プロジェクト全体の原則）と、受け入れ基準から導かれたテスト群。この 2 つは常に現実と同期させる
- **凍結してよいもの**: 完了した機能の spec / plan / tasks。これらは「その機能がなぜ・どう作られたか」の**歴史的記録（ADR に近い性格）**として残し、変更が必要になったら新しい仕様ディレクトリを切る

「仕様」という一語に「現在の振る舞いの記述」と「変更の提案書」の 2 つの役割を混ぜないことが、メンテナンス戦略の核心です。

### 6.5 仕様変更の 2 方式 — 凍結して新規に切るか、既存を修正するか

新たな要求が発生したとき、取れる方式は 2 つあります。§6.4 の割り切りを前提に、それぞれの得失と使い分けを整理します。

**方式 A: 追記型（実装済み spec は凍結し、新しい spec を切る）**

実装が完了した spec には手を触れず、変更・追加要求はすべて新しい機能ディレクトリ（`specs/002-*` …）として起こす方式です。Spec-kit の「機能ブランチ = 仕様ディレクトリ」モデルの素直な運用であり、OpenSpec など「変更提案（change proposal）」を第一級に据えるツールも同じ思想です。

- 利点: 「なぜ変えたか」が差分ではなくドキュメントとして残る（ADR と同じ性質）。凍結された過去の spec が古びても実害がない。並行する複数の変更が衝突しにくい
- 欠点: **「現在の振る舞いの全体像」がどこにも存在しなくなる**。001 と 002 と 007 を重ね合わせないと現状が分からない状態は、それ自体が新しいドリフトです

**方式 B: 修正型（既存 spec を直して再実装する）**

既存の spec.md を直接修正し、plan / tasks / 実装を更新する方式です。spec は常に「現在の振る舞い」を表し続けます（spec-anchored の教科書的な形、§6.2）。

- 利点: 現状が常に 1 箇所で分かり、仕様が文字通りの source of truth になる
- 欠点: 変更の経緯と理由が Git log に沈む。§6.4 の「凍結してよい」割り切りが使えず、**全 spec の鮮度維持コストを払い続ける**。完了済み spec の再オープンは Spec-kit の機能ブランチモデルとやや相性が悪い（Kiro は既存 spec のセッション再開が UI 上サポートされており、方式 B 寄りの設計です）

**推奨: 判断基準は「既存の受け入れ基準を書き換えるか」**

- 既存機能の受け入れ基準に触れない**純粋な追加**（新機能・新ストーリー） → 方式 A で新しい spec を切る
- 既存の受け入れ基準を**変える・置き換える**変更 → 新しい spec を切った上で、旧 spec の該当箇所に「superseded by 002」のマークを付け、**「現在の振る舞い」は L1（`specs/_product/`、§10.2）と受け入れテストに反映する**

つまり実務解は「機能 spec は追記型で運用し、現在形の維持は L1 とテスト群に委ねる」というハイブリッドです。方式 A の欠点（現在形の不在）を L1 が補償し、方式 B の欠点（全量の鮮度維持）は L1 の数ファイルに局所化される——§6.4 の 2 層の割り切りと §10 の階層構造は、この変更方式を成立させるための仕掛けでもあります。

### 6.6 バグが発生したときのプラクティス

SDD ではバグ対応の最初の一手が「コードを見る」ではなく「**仕様のどこに違反しているかを指さす**」に変わります。指させ方によってバグは 3 種類に分類でき、それぞれ扱いが異なります。

| 分類 | 状態 | spec の扱い |
|---|---|---|
| **実装バグ** | 仕様は正しいが、実装が受け入れ基準を満たしていない | **触らない** |
| **仕様バグ** | 実装は仕様通りだが、仕様自体が間違っていた・曖昧だった | **修正する**（§6.5 の方式選択に従う） |
| **仕様の欠落** | そのケースについて仕様が沈黙しており、実装の自由裁量が埋めていた | **追加する**（受け入れ基準を足す） |

- **実装バグ**は SDD のフルワークフローを回す必要がありません（§4.2）。再現を受け入れ基準対応の失敗するテストとして書き、修正して閉じます。エージェントに投げる場合もバグレポートと関連テスト・コードだけで足り、spec 全体を読み込ませる必要はありません（§10.1 の「都度」層の切り出しがここで効きます）。ただし同じ箇所で再発するなら、受け入れテストの欠落を疑ってテストを補強します
- **仕様バグ**は §7.4 でいう正当性の問題です。「実装は正しく動いている」ため通常のデバッグでは原因に到達できず、仕様に遡って直すしかありません。受け入れ基準の書き換えを伴うので §6.5 の基準に従い、影響が大きければ新 spec（superseded マーク付き）、軽微な明確化なら凍結 spec への注記追記で処理します。曖昧さが原因だった場合は、該当の受け入れ基準を判定可能な形（§7.6）に書き直すところまでが修正です
- **仕様の欠落**は、エージェントの自由裁量が隙間を埋めた場所で起きる SDD 特有の典型パターンです（§7.6 の「暗黙知の欠如」の帰結）。望ましい振る舞いをまず要求として決定し（これは実装判断ではなく要求定義です）、受け入れ基準を追加してから修正します。あわせて spec の「スコープ外」リストを拡充し、同種の隙間を塞ぎます。なお Kiro はバグ修正にも spec ワークフローを適用する前提の設計で、この分類を UI 上で強制するイメージに近いものです

最後に、この分類は**プロセス改善の計器**になります。実装バグが多いなら implement とテスト接続（§6.3-4）の問題、仕様バグ・欠落が多いなら specify / clarify の質の問題です。バグ票に 3 分類のラベルを付けておくだけで、「仕様レビューを厚くすべきか、テストを厚くすべきか」がデータで判断できるようになります。

## 7. 仕様の粒度 — ソフトウェア工学的位置付け

「仕様の粒度をどう取るか」は Spec-kit 固有の問題ではなく、**要求工学（requirements engineering）が数十年扱ってきた問題**の再演です。ここでいう仕様とは、いわゆる**要求仕様（requirements specification）**——要求を厳密に定義して記述したもの——であり、要求仕様には正当性・厳密性・可読性・検証可能性・実現性といった複数の品質特性が求められ、しかもそれらは**互いにトレードオフ**します。粒度とは独立したつまみではなく、**このトレードオフ空間のどこに立つかを決める操作変数**です。本章はその順で解像度を上げていきます。

### 7.1 要求工学の抽象度スタックへの対応

古典的な要求工学（ISO/IEC/IEEE 29148 などが体系化）では、要求を抽象度のスタックで捉えます。Spec-kit の成果物はこのスタックにきれいに対応します。

| 抽象度レイヤー | 古典的な文書 | Spec-kit での対応物 |
|---|---|---|
| ビジネス要求（なぜやるか） | ビジネスケース、憲章 | constitution ＋ spec の背景記述 |
| ユーザー要求（誰が何をできるか） | ユーザーストーリー、ユースケース | **spec.md**（ユーザーストーリー・受け入れ基準） |
| システム要求・設計（どう実現するか） | SRS の設計制約、設計書 | **plan.md**（技術選定・アーキテクチャ・契約） |
| 作業分解（どの順で作るか） | WBS、チケット | **tasks.md** |

つまり Spec-kit は新しい概念を発明したのではなく、**要求工学の抽象度スタックを AI エージェントが消費可能なファイル形式に再実装したもの**と位置付けられます。

### 7.2 「What と How の分離」= 宣言的仕様と手続き的計画

仕様の粒度を誤る典型は、**抽象度の混入**です。spec.md に「PostgreSQL のテーブル設計」が書かれた瞬間、その仕様は技術変更で腐り始め、逆に plan.md に「ユーザーは〜できるべき」が紛れ込むと、要求の出所が追跡できなくなります。

- 仕様は**宣言的**であるべき: 観測可能な振る舞いと受け入れ基準を記述し、実現手段に言及しない
- 計画は**手続き的**でよい: 技術決定とその根拠（rationale）を記述し、各決定が仕様のどの要求に由来するかをトレースできるようにする

この分離は契約による設計（Design by Contract）の考え方——インターフェース（何を保証するか）と実装（どう満たすか）の分離——の、ドキュメントレベルへの適用と見ることができます。**仕様ドリフトの主因の多くは、この抽象度の混入**です（技術詳細が仕様に書かれていると、リファクタリングのたびに仕様が「嘘」になる）。要求工学の用語では、この「実現手段に言及しない」性質は**解決策非依存性（implementation-free）**と呼ばれ、次節で見る品質特性の一つに数えられます。

### 7.3 要求仕様の品質特性 — 粒度を規定する力

要求工学の標準（ISO/IEC/IEEE 29148 が代表）は、「良い要求仕様」の品質特性を明示的に定義しています。**個々の要求**に求められるものと、**要求の集合（仕様書全体）**に求められるものは区別され、粒度はその両方に効きます。

**個々の要求の品質特性**

| 特性 | 意味 | 粒度との関係 |
|---|---|---|
| 非曖昧性（unambiguous） | 読み手によって解釈が分かれない | 粗い記述は曖昧さの温床になる |
| 検証可能性（verifiable） | 充足をテスト・検査で客観的に判定できる | 判定可能な単位まで分解する圧力が働く |
| 単一性（singular） | 1 要求は 1 つの事柄だけを述べる | 粒度の下限を直接定義する特性 |
| 実現可能性（feasible） | 技術・コスト・期限の制約内で実現できる | 実現性の確認には設計への「先読み」が要る |
| 解決策非依存性（implementation-free） | 実現手段を拘束しない | 細かくしすぎると設計の先取りが混入する |
| 必要性（necessary） | 削除すると何かが成立しなくなる | 過剰な細分化は不要要求を生む |

**要求の集合の品質特性**

| 特性 | 意味 | 粒度との関係 |
|---|---|---|
| 完全性（complete） | 必要な要求がすべて含まれる | 細かくするほど「完全に見える」が錯覚しやすい |
| 無矛盾性（consistent） | 要求同士が衝突しない | 要求数 n に対し検査すべき組合せは O(n²) で増える |
| 追跡可能性（traceable） | 要求↔設計↔テストを相互に辿れる | 細かいほどトレースは張りやすいが維持コストも増える |

そして、これらすべての前提となるのが**正当性（validity / correctness）**——そもそも利害関係者の真の要求を捉えているか——です。重要なのは、正当性だけは**仕様書の内部だけを見ても判定できない**ことです（検証 verification ではなく妥当性確認 validation の問題）。この非対称性が、後述するトレードオフの中で決定的な役割を果たします。

### 7.4 品質特性はトレードオフする — 粒度はその調停変数

これらの特性は同時に最大化できません。要求仕様の設計とは、実質的に次のようなトレードオフの調停です。

1. **厳密性 vs 可読性**: 形式手法（Z、VDM、TLA+ など）は曖昧さを排除し機械検証まで可能にしますが、利害関係者が読めなくなり、正当性の確認（「これは本当に欲しいものか」）が困難になります。自然言語は誰でも読めますが曖昧です。EARS 記法（§8.1）や Gherkin はこの中間を狙った**半形式**の発明であり、Spec-kit の「ユーザーストーリー＋判定可能な受け入れ基準」も同じ立ち位置です
2. **完全性 vs 保守性・無矛盾性**: 要求を網羅しようとするほど仕様書は肥大化し、無矛盾性の維持コストは組合せ的に増え、変更時に直し漏れる箇所（＝ドリフトの発生源、§6.1）が増えます。「完全な仕様」を追うことは、腐りやすい仕様を作ることと裏腹です
3. **検証可能性 vs 抽象度・安定性**: 「応答は十分速いこと」は検証不能ですが、「95 パーセンタイルで 200ms 以下」は検証可能な代わりに、その数字自体が設計判断の先取りかもしれず、環境が変われば腐ります。検証可能にするための具体化は、解決策非依存性・安定性を削って買うものです
4. **実現性 vs 解決策非依存性**: 要求が実現可能かを保証するには設計・技術を検討せざるを得ず、純粋に「What だけ」を書いた仕様は実現性を担保できません。SDD ツールはこの矛盾を**フェーズ分離で時間差解決**しています——spec は解決策非依存に書き、実現性の確認は plan（Spec-kit なら research を含む）で行い、矛盾が見つかれば spec に差し戻す
5. **正当性 vs その他すべて**: 最も見落とされがちなトレードオフです。厳密で検証可能で完全に見える仕様が、**間違った要求を精密に記述している**ことはあり得ます。むしろ形式が整っているほど権威的に見え、妥当性確認が素通りしやすくなります。LLM が流暢な仕様を大量生成できる現在、この罠は構造的に深刻化しています（§4.4 で「要求の妥当性」を人間のゲートに挙げた理由がこれです）

この整理の上で、粒度の効き方を一言でまとめると次の通りです。

> **粒度を細かくする**と、非曖昧性・検証可能性・単一性・追跡可能性が上がる。代わりに、仕様書全体の可読性が下がり、無矛盾性の維持コストが増え、設計の先取り（解決策非依存性の侵食）と不要要求が混入し、人間が正当性を確認しきれる量を超えていく。**粒度を粗くする**と、その逆が起きる。

つまり「適切な粒度」なるものが単独で存在するのではなく、**そのプロジェクトでどの品質特性を優先するかを決めて初めて、粒度が決まる**——これが要求工学から見た粒度の位置付けです。

### 7.5 古典理論との接続

- **Parnas の情報隠蔽（1972）**: モジュール仕様は「何を提供するか」だけを公開し「どう実装するか」を隠す。SDD の spec/plan 分離はこの原則の文書版であり、「仕様は実装の変更に対して安定」という性質もそのまま引き継ぐ
- **BDD / 実行可能仕様（Specification by Example）**: 受け入れ基準を具体例で書き、テストとして実行する系譜。SDD の受け入れ基準→テスト接続（§6.3-4）は BDD の直系で、「実行できる仕様だけがドリフトを検出できる」という教訓も共通
- **INVEST 原則**: アジャイルのストーリー分割基準（Independent / Negotiable / Valuable / Estimable / Small / Testable）。`/speckit.tasks` が生成するタスクの品質を評価する物差しとしてそのまま使える

### 7.6 LLM 時代に粒度が「第一級の設計問題」に戻った理由

人間チームでは、仕様の粒度が粗くても暗黙知と対話が補ってくれました。LLM エージェントの登場は、§7.4 のトレードオフの**価格体系そのものを動かし**、粒度の設計を再び決定的にしています。

- **曖昧さのコストが即時化した**: 人間なら質問で埋めた隙間を、エージェントは自由裁量（＝過剰設計やハルシネーションの温床）で埋める。非曖昧性の価値が跳ね上がった
- **厳密性のコストが暴落した**: EARS や Gherkin で網羅的に書く記述コストは、生成が LLM 化されたことでほぼ消えた（Kiro の EARS 標準採用はこの前提の上にある）。「厳密に書く手間」はもはや粒度を粗くする理由にならない
- **検証可能性が「実行可能性」になった**: 判定可能な受け入れ基準はそのままテストとして実行でき（§6.3）、ドリフト検出まで自動化される。検証可能性への投資の回収率が上がった
- **コンテキストウィンドウという新しい物理制約が加わった**: 1 タスクの仕様＋関連コードがコンテキストに収まらなければ品質が落ちる（§9.1）。粒度の上限が美学ではなく容量で規定されるようになった
- **唯一値下がりしないのが正当性の確認**: 仕様の生成・厳密化・検証は安くなったが、「これは本当に作るべきものか」を判断できるのは依然として人間だけで、その人間のレビュー容量は増えていない。**正当性確認が新しいボトルネック**であり、人間が妥当性を確認しきれない量の要求を生成することは、完全性の見かけを上げながら正当性を毀損する

そこから導かれる実践的な粒度の基準は次の 3 条件です。

> 1 つのタスクは、**(1) 関連コンテキストごとエージェントのコンテキストに収まり、(2) 受け入れテストで完了を機械的に判定でき、(3) 独立してレビューできる**単位に切る。

spec 側の粒度はこう整理できます: **下限**は単一性と検証可能性（受け入れ基準が曖昧さなく判定可能であること）、**上限**は解決策非依存性（それより細かい実現手段は plan に送る）と、人間の正当性レビュー容量（読んで妥当性を判断しきれる量）が定めます。従来どおり **「仕様は判定可能性で、タスクはコンテキスト容量で切る」** が実務の第一近似ですが、その正体は§7.4 のトレードオフ空間で「非曖昧性・検証可能性を最優先し、完全性は正当性レビューが追いつく範囲に抑える」という**優先順位の選択**である——というのが、解像度を上げた答えです。

## 8. AWS Kiro との比較

SDD の実装として Spec-kit と並んでよく比較されるのが AWS の **Kiro** です。同じ「仕様→設計→タスク→実装」の思想を、まったく異なる提供形態で実現しており、どちらを選ぶかはチームの環境と志向に依存します。

### 8.1 Kiro の概要

Kiro は AWS が提供する **Agentic IDE** です（Code OSS ベースの独立エディタ。Claude を Amazon Bedrock 経由で利用）。2025 年 7 月にプレビュー公開され、**2026 年 3 月に GA**、同年 5 月に国際展開されました。位置付けとしては Amazon Q Developer の実質的な後継です。

仕様ワークフローは Spec-kit の読者にはすぐ対応が取れます。

- 1 機能 = `requirements.md` → `design.md` → `tasks.md` の 3 ファイル（Spec-kit の spec / plan / tasks に相当）
- `requirements.md` はユーザーストーリーごとに **EARS 記法**（Easy Approach to Requirements Syntax: 「When 〜, the system shall 〜」形式）で受け入れ基準を網羅的に記述する
- **steering ファイル** がプロジェクト全体の原則を保持（Spec-kit の constitution に相当）
- Spec-kit にない差別化機能として、**Agent Hooks**（ファイル保存などをトリガーにエージェントを自動起動。テスト更新やドキュメント同期の自動化に使う）と、autopilot / supervised の実行モード切り替えがある

### 8.2 比較表

| 観点 | Spec-kit | Kiro |
|---|---|---|
| 提供形態 | CLI ＋ プロンプト・テンプレート集（OSS） | 統合 IDE（Code OSS フォーク） |
| 対応エージェント | 30+（Claude Code, Copilot, Cursor, Gemini CLI…） | Kiro 内蔵エージェントのみ（モデルは Claude 系） |
| 導入方法 | 既存環境にスラッシュコマンドを追加するだけ | エディタごと移行（VS Code 拡張は Open VSX 互換のみ、Marketplace 非対応） |
| 仕様の構成 | constitution + spec / plan（research 等に分割）/ tasks | steering + requirements / design（単一ファイル）/ tasks |
| プロセスゲート | clarify / analyze / checklist と多段 | requirements → design → tasks の承認ステップ ＋ GUI での進捗管理 |
| 要求記述 | コアなユーザーストーリー中心 | EARS 記法で受け入れ基準を網羅的に生成 |
| コスト | ツール自体は無料（既存エージェント契約のトークン消費のみ） | クレジット制サブスクリプション（下記） |
| ロックイン | ほぼなし（生成物はただの Markdown） | IDE・AWS エコシステムに依存 |

### 8.3 観点別の優位性

**使いやすさ — オンボーディングは Kiro、環境適合性は Spec-kit**

- Kiro の強みは統合された体験です。SPECS / AGENT HOOKS / STEERING が GUI パネルで見え、タスクの進捗が視覚的にトラッキングされ、承認フローもクリックで進みます。「まず SDD がどういうものか体験する」導入ハードルは最も低い部類です
- Spec-kit の強みはエディタ非依存であることです。VS Code でも Vim でも普段の環境にそのまま足せて、既に使っている Claude Code / Copilot の契約・設定・スキルがそのまま活きます。CLI 派・環境を変えたくないチームはこちらです
- Kiro の注意点: UI は英語に最適化されており、拡張機能は Open VSX 互換のものに限られます（VS Code Marketplace 非対応）

**コスト — 予見性の Kiro、追加費用ゼロの Spec-kit**

- Spec-kit は無料の OSS で、コストは背後のエージェント（Claude Code 等）のトークン消費だけです。既にエージェント契約があるチームは**追加費用ゼロ**で始められます
- Kiro はクレジット制です: Free $0（50 クレジット/月）、Pro $20（1,000）、Pro+ $40（2,000）、Pro Max $100（5,000）、Power $200（10,000）。超過は $0.04/クレジットで、選択モデルにより消費倍率が変わります（例: Claude Opus 4.8 は 2.2 倍）
- クレジット制はタスクごとのコストが見えやすい（従量の予見性が高い）反面、仕様生成・タスク分解・フック実行のすべてがクレジットを消費するため、SDD のフルワークフローを回すほど消費が速く、月中の枯渇リスクがあります。Free の 50 クレジットは試用向けで、実務は Pro 以上が前提です

**品質 — 要求の網羅性は Kiro、プロセスの厳密さは Spec-kit**

- Kiro は EARS 記法により受け入れ基準の**網羅性**が高く、エッジケースの拾い漏れが少ない傾向があります。要求定義フェーズの生成物の密度では優位です
- Spec-kit は clarify（曖昧さの対話的解消）・analyze（成果物間の整合性検証）・checklist という**プロセスゲートの多段構成**と、plan フェーズが research・data-model・contracts などに分割され調査が厳密である点で優位です。Kiro の design.md は単一ファイルで、既存プロジェクト理解は得意な一方、最新技術情報の調査フェーズは比較的浅いという評価が一般的です
- ただし §4・§6 で述べた通り、**最終的な品質を決めるのはツールではなく、仕様レビューの規律と constitution / steering の初期品質**です。どちらを選んでも「仕様レビューをスキップすれば重い vibe coding になる」点は変わりません

### 8.4 使い分けの指針

- **Spec-kit を選ぶ**: 既に Claude Code / Copilot 等の契約・運用資産がある。エディタを変えたくない。プロセスの厳密さ（clarify / analyze）を重視する。ベンダーロックインを避けたい
- **Kiro を選ぶ**: AWS エコシステム中心のチーム。GUI での進捗可視化や承認フローを重視する。Agent Hooks による自動化（保存時テスト・ドキュメント同期）に魅力を感じる。SDD 未経験メンバーが多くオンボーディングを優先したい
- **共通の注意**: どちらも小さなタスクには過剰です（§4.2）。また生成物はどちらも Markdown なので、spec ↔ requirements の相互移行は比較的容易であり、「まず Spec-kit で試して、チームが SDD に馴染んだら IDE ごと Kiro を検討する」（またはその逆）という段階的な選択も現実的です

## 9. コンテキストエンジニアリングの基礎と応用

SDD がなぜ効くのか、なぜ「仕様をファイルに書く」だけでエージェントの品質が変わるのかは、**コンテキストエンジニアリング**の基礎を押さえると原理から理解できます。Spec-kit と Kiro の設計判断は、ほぼすべてここに根拠があります。

### 9.1 基礎: LLM エージェントの「作業記憶」の性質

**プロンプトエンジニアリングとの違い。** プロンプトエンジニアリングが「1 回の指示文をどう書くか」の最適化だとすれば、コンテキストエンジニアリングは「**エージェントが行動するその瞬間に、何を知り、何を見て、何を覚えているか**」という情報環境全体の設計です。マルチステップで動くエージェントでは、指示文はコンテキストの一部にすぎません。エージェントのコンテキストは、おおまかに次の要素で構成されます。

- システムプロンプト（役割・制約）
- ツール定義
- 取得データ（読んだファイル、検索結果）
- 会話履歴（過去のやりとり、ツールの実行結果）
- メモリ（セッションを跨いで持ち込まれる情報）

**コンテキストウィンドウは有限の作業記憶。** LLM の注意（attention）は有限の予算であり、コンテキストに積むトークンが増えるほど 1 トークンあたりに向けられる注意は薄まります。「たくさん読ませるほど賢くなる」は成り立ちません。

**コンテキストロット（context rot）。** さらに悪いことに、劣化は線形ではありません。コンテキストが埋まるにつれ、モデルは直近のトークンを優先し、中間や冒頭の情報の想起精度が落ちていきます（2026 年時点の経験則では、およそ 50% を超えると中間軽視が顕著になり、75% を超えると精度が急落する）。**「長いチャットセッションほどエージェントが当初の指示を忘れ、質が落ちていく」現象の正体がこれ**であり、§1 で挙げた vibe coding のドリフトの技術的説明でもあります。

### 9.2 応用: 長時間タスクを成立させる 4 つのパターン

コンテキストという希少資源を管理するための実践パターンは、Anthropic の整理（[Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)）に沿えば次の 4 つに集約されます。

1. **Just-in-Time 取得**: 必要になりうる情報をすべて前積みせず、ファイルパスや検索手段だけを渡して、必要になった時点でエージェント自身に取得させる。人間が「全部暗記」せず「どこに書いてあるか」を覚えるのと同じ戦略
2. **コンパクション（要約圧縮）**: 会話履歴を要約して容量を回復する。ポイントは限界が来てからの事後対応にせず能動的に行うこと、そして**残すもの（設計判断・ファイルパス・制約）と捨てるもの（生のツール出力・エラートレース）を明示的に指定する**こと
3. **構造化メモ / 外部メモリ**: 重要な決定・進捗をコンテキストの外＝ファイルに書き出して永続化し、必要なときに読み戻す。コンテキストは揮発するが、ファイルは揮発しない
4. **サブエージェント**: 調査など大量のコンテキストを消費する作業を別コンテキストのエージェントに隔離し、凝縮された結論だけを親に返させる。親のコンテキストを本題のために温存する

### 9.3 SDD はコンテキストエンジニアリングの「制度化」である

ここまで来ると、Spec-kit の設計がこの 4 パターンの**ファイル規約への落とし込み**であることが見えてきます。

| コンテキストエンジニアリングの原理 | Spec-kit での実装 | Kiro での実装 |
|---|---|---|
| 常駐させるべき恒久コンテキストの分離 | constitution | steering ファイル |
| 構造化メモ / 外部メモリ | spec.md / plan.md / tasks.md | requirements / design / tasks |
| Just-in-Time 取得の単位 | 機能ごとの `specs/NNN-*/` ディレクトリ | 機能ごとの spec セッション |
| コンテキスト消費の大きい作業の隔離 | plan の research 分割、タスク単位の実装 | 承認ステップで区切られたフェーズ実行 |

この対応関係から、本ドキュメントの主張のいくつかが原理側から裏付けられます。

- **§2.1「プロンプトの使い捨てをやめる」の技術的根拠**: チャットログはコンテキストロットで劣化し、セッション終了で消える。ファイル化された仕様は劣化せず、新しいセッションが常にフレッシュなコンテキストで読み直せる
- **§7.6「タスクはコンテキスト容量で切る」の理論的裏付け**: タスク粒度の 3 条件は、コンテキストロットが起きる前に 1 タスクを完結させるための設計である
- **§4.5「constitution の初期品質が全体を左右する」の理由**: constitution は全フェーズのコンテキストに常駐する唯一のファイルであり、ここに書かれた 1 行はすべての判断に効き続ける（逆に曖昧な 1 行はすべての判断を汚染する）

要するに、**SDD とは「コンテキストエンジニアリングをツールの使い方から、チームのファイル規約と開発プロセスに昇格させたもの」**と理解するのが、2026 年時点で最も見通しの良い整理です。

## 10. ベストな spec 構成 — コンテキストと粒度から導く階層設計

§7（粒度）と §9（コンテキスト）の帰結として、「では実際にどういうファイル構成を取るのがベストか」をここで導きます。結論から言うと、仕様を内容で分類するのではなく、**「エージェントのコンテキストにどう読み込まれるか」で層別し、層ごとに寿命とトークン予算を決める**のが、コンテキスト長と粒度の両方に整合する構成です。

### 10.1 設計原理: 「読み込まれ方」から逆算する

仕様ファイルは、コンテキストへの載り方で 3 種類に分かれます。この区別が構成のすべての土台です。

| 読み込まれ方 | 該当物 | 設計制約 |
|---|---|---|
| **常駐**（全セッション・全フェーズで必ず載る） | constitution / steering | 1 行がすべての判断に課税される（§4.5）。最小・不変・厳選 |
| **都度**（関連する作業の間だけ載る） | spec / plan / ドメインモデル | 自己完結していて、必要な部分だけ切り出せる粒度で書く |
| **使い捨て**（生成時に読まれ、以後ほぼ参照されない） | research / 完了した tasks | 肥大化してよい。ただし常駐・都度の層に絶対に混ぜない |

もう 1 つの原理が**コンテキスト予算の逆算**です。実装時にエージェントが読むのは「常駐層 ＋ 対象機能の仕様・計画 ＋ 当該タスク ＋ 関連コード」の合計で、コンテキストロットを避けるにはこれをウィンドウの 50% 以内に収めたい（§9.1）。関連コードが最大かつ制御しにくい変動要素なので、**仕様側の合計を先に固定予算として切る**（目安: 常駐層 1〜2K トークン、機能単位の仕様＋計画で 5〜10K トークン。Markdown はおおむね 1 行 ≒ 10〜15 トークン）のが実務的な解です。

### 10.2 推奨階層構造

上の原理を Spec-kit の規約に載せると、次の 4 層構造になります（`.specify/templates/` 等のツール管理物は省略）。

```
リポジトリルート
├── .specify/memory/
│   └── constitution.md          # L0: 常駐層（〜100行）
│                                #   不変の原則のみ: 品質基準・技術方針・
│                                #   単純さの原則・テスト規律
├── specs/
│   ├── _product/                # L1: プロダクト恒久層（生きたドキュメント）
│   │   ├── overview.md          #   プロダクト全体像と機能マップ（〜150行）
│   │   ├── glossary.md          #   用語集 = チームの暗黙知の明文化（〜100行）
│   │   └── domain-model.md      #   ドメインモデルと不変条件（〜300行）
│   │
│   └── 001-user-auth/           # L2: 機能層（完了後は凍結、§6.4–6.5）
│       ├── spec.md              #   What/Why: ストーリー＋受け入れ基準（100〜200行）
│       ├── plan.md              #   How: 技術決定とその根拠（100〜200行）
│       ├── research.md          #   使い捨て層: 調査ログ（上限なし）
│       ├── contracts/           #   必要時のみ: API 契約・データモデル等の分割
│       └── tasks.md             # L3: タスク層（1タスク=1コンテキストの単位）
└── tests/acceptance/            # 受け入れ基準の実行形（§6.3: 最強のドリフト検出器）
```

各層の性格をまとめると次の通りです。

| 層 | 寿命 | 粒度の支配原理 | 予算の目安 |
|---|---|---|---|
| L0 constitution | 不変（変更はチーム合意） | 全判断への課税を最小化 | 〜100 行（1〜2K トークン） |
| L1 _product/ | 生きたドキュメント（常に現実と同期） | 1 ファイル 1 関心事・自己完結 | 各ファイル 〜300 行 |
| L2 機能ディレクトリ | 完了後は凍結（歴史的記録） | 判定可能性（§7.6 の下限）と 1 機能の独立性 | spec＋plan で 5〜10K トークン |
| L3 tasks.md | 実装期間のみ | コンテキスト容量（§7.6 の 3 条件） | 1 タスク = 変更 5 ファイル以内が目安 |

素の Spec-kit と違うのは **L1（`specs/_product/`）を明示的に設けている**点です。Spec-kit の標準構成は機能単位（L2）が中心で、機能横断の知識は constitution に吸い込まれがちですが、ドメインモデルや用語集は「不変の原則」ではなく「生きた現実」なので、常駐層に置くと L0 が肥大化します。L1 に分離し、`/speckit.specify` や `/speckit.plan` の際に**参照すべきファイルとして明示的に渡す**（都度読み込み）のが、予算と鮮度の両立点です。Kiro でも steering を L0 相当に絞り、L1 相当をプロジェクト内 Markdown として持つ同型の構成が取れます。

### 10.3 spec.md の内部構成と分割トリガー

L2 の spec.md 自体の推奨構成です。§7 のトレードオフでいえば「非曖昧性・検証可能性を最優先し、完全性はレビュー容量の範囲で」という優先順位をテンプレートに焼き込みます。

```markdown
# 001: ユーザー認証          ← 機能名と番号
## 背景と目的（Why）          ← 3〜10行。L1 overview へのリンクで重複を避ける
## ユーザーストーリー（What）  ← 3〜7個。それ以上なら機能分割のサイン
## 受け入れ基準               ← ストーリーごとに3〜7個、判定可能な形（EARS/Gherkin 風）
## スコープ外                 ← 明示的に書く。エージェントの自由裁量を塞ぐ（§7.6）
## 非機能要件                 ← 該当分のみ。数値は根拠とセットで（§7.4-3）
```

分割・昇格のトリガーは次の通りです。

- **ユーザーストーリーが 7 個を超えた** → 機能を分割する。分割は必ず**ユーザー価値の縦切り**（例: 「ログイン」と「パスワードリセット」）にし、アーキテクチャ層の横切り（「DB 層」「API 層」）にしない。横切りは独立して受け入れテストできず、§7.6 の 3 条件を満たせない
- **spec＋plan が予算（5〜10K トークン）を超えた** → まず plan の詳細を `contracts/` 等へ分割、それでも超えるなら機能自体を分割
- **複数の機能ディレクトリが同じ事実を書き始めた** → その事実を L1 に昇格させ、各 spec からは参照に置き換える（事実の単一ソース化）
- **L1 のファイルが 300 行を超えた** → 関心事で分割（例: domain-model.md から支払いドメインを独立させる）

### 10.4 アンチパターン

- **巨大な単一 SPEC.md**: 全機能を 1 ファイルに書くと、どのタスクでも全体が読み込まれ、予算が即座に破綻する。「都度」層は切り出し可能性がすべて
- **constitution の肥大化**: 便利な知識を何でも常駐層に入れると、全タスクが恒常的に課税される。「これは不変の原則か、生きた事実か」で L0/L1 を仕分ける
- **4 階層を超えるネスト**: エージェントはファイルパスを手がかりに Just-in-Time 取得する（§9.2）。深いネストは発見可能性を下げる。L0〜L3 の 4 層で足りない場合、たいてい機能の切り方（縦割り）に問題がある
- **research の常駐化**: 調査ログは仕様ではない。plan に結論だけを書き、research.md は「なぜその結論か」を辿るときだけ読む使い捨て層に留める
- **同じ事実の重複記述**: コードの DRY と同じで、重複した事実は必ず片方だけが更新されドリフトの発生源になる。事実は 1 箇所に書き、他は参照する

この構成が「ベスト」である根拠は、突き詰めれば §7.6 と §9 の 2 点に帰着します: **常駐・都度・使い捨ての層別がコンテキスト予算を守り（コンテキスト長への解）、判定可能性で切った spec とコンテキスト容量で切ったタスクが各層の粒度を定める（粒度への解）**。プロジェクト規模によって L1 を省略する（小規模）、L2 をサブシステムごとに分ける（大規模）といった調整はあり得ますが、この層別の原理自体は規模によらず有効です。

## 11. ハーネスエンジニアリング — SDD を包む上位概念

2026 年に入って一気に一般化した用語に**ハーネスエンジニアリング（harness engineering）**があります。本ドキュメントで扱ってきた constitution・仕様の階層・受け入れテスト・フックは、実はすべてこの概念の部品です。ここで全体を紐付けて整理します。

### 11.1 ハーネスエンジニアリングとは

出発点は **Agent = Model + Harness** という分解です。エージェントの能力はモデル単体で決まるのではなく、モデルを包む「ハーネス（馬具）」——利用できるツール、参照するファイル、検証の仕組み、ガードレール、監視——との積で決まります。ハーネスエンジニアリングとは、**このハーネス側を体系的に設計・改善する規律**のことで、2026 年初頭に OpenAI のエンジニアが「人手で 1 行も書かずに本番アプリケーションを出荷した」経験から定式化した記事を契機に広まりました（用語自体の一般化は 2026 年前半）。

構成要素は論者によって多少異なりますが、おおむね次の 5 層に整理されます。

1. **ルール・指示**: エージェントに常駐で与える行動規範・規約
2. **コンテキストと記憶**: 何をいつコンテキストに載せるかの設計
3. **ツールオーケストレーション**: 使えるツールの選定と接続
4. **検証ループ**: 生成物を機械的に検証し、自己修正させる仕組み
5. **ガードレール・可観測性**: してはいけないことの強制と、挙動の監視

そして中核にあるのが次の運用原則です。

> **エージェントが間違えたら、その場で直すだけで終わらせず、「二度と同じ間違いをしない」ようハーネス側を直す。**

プロンプトを工夫して 1 回の成功率を上げるのではなく、失敗をハーネスの改善に変換し続けることで、エージェントの信頼性を**蓄積可能な資産**にする——これがこの概念が「今年の話題」になった理由です（モデルの更新よりハーネスの改善のほうが実効性能を大きく動かした、という分析も広まりました）。

### 11.2 本ドキュメントとの紐付け — 既に書いてあることの再配置

実は本ドキュメントの内容は、ハーネスの 5 層にそのまま対応します。SDD はハーネスエンジニアリングの一形態（仕様を中心に据えた実装パターン）だった、というのが正確な位置付けです。

| ハーネスの層 | 本ドキュメントでの既出箇所 |
|---|---|
| ルール・指示 | constitution / steering（§3.1、§4.5「初期品質が全体を左右する」） |
| コンテキストと記憶 | §9 コンテキストエンジニアリング全体、§10 の常駐・都度・使い捨ての層別 |
| ツールオーケストレーション | `/speckit.*` コマンド群（§3.1）、Kiro の Agent Hooks（§8.1） |
| 検証ループ | 受け入れ基準のテスト接続・`/speckit.analyze` の CI 化（§6.3）、バグの 3 分類（§6.6） |
| ガードレール・可観測性 | 人間がゲートすべき観点（§4.4）、スコープ外の明示（§10.3）、バグ分類統計によるプロセス改善（§6.6） |

「間違えたら二度と間違えないようハーネスを直す」という中核原則も、既に本ドキュメントに 2 回登場しています: §13 の始め方ステップ 4（エージェントが暴走した箇所を constitution に還元する）と、§6.6 のバグ分類統計（実装バグが多ければテスト接続を、仕様バグが多ければ specify/clarify を直す）です。どちらも「失敗をハーネスの改善に変換するループ」の具体例です。

### 11.3 エージェンティックコーディングの必須ファイル群

ハーネスの実体は、リポジトリに置かれる少数のファイル群です。Claude Code を例に、それぞれの役割と、§10 の「読み込まれ方」との対応を整理します（他のエージェントもほぼ同型の仕組みを持ちます）。

| ファイル | 役割 | ハーネス層 | 読み込まれ方（§10.1） |
|---|---|---|---|
| `CLAUDE.md` / `AGENTS.md` | エージェントへの常駐指示（規約・ビルドコマンド・注意事項）。`AGENTS.md` は複数エージェント共通のオープン標準で、ツール横断の可搬性がある | ルール・指示 | **常駐**（毎セッション読み込まれる。§10 の L0 と同じ予算規律が必要） |
| `.claude/skills/*/SKILL.md` | **Skills**: 手順知識のパッケージ（例: 社内のリリース手順、特定フレームワークの流儀）。冒頭の説明だけが常駐し、本文は該当タスクのときだけ読み込まれる（progressive disclosure） | コンテキストと記憶 | **都度**（常駐コストを払わずに専門知識を持たせる仕組み） |
| **hooks**（`settings.json` 内） | ツール実行の前後や停止時に、**決定論的に**スクリプトを実行する（例: 編集後に必ず lint とテスト、危険コマンドのブロック）。LLM の確率的な判断に任せない品質ゲート | 検証ループ／ガードレール | コンテキスト外（LLM を経由せず必ず実行される点が本質） |
| `.claude/agents/*.md` | **サブエージェント**定義: 役割特化のエージェント（レビュー専任、調査専任など）。§9.2 のコンテキスト隔離パターンの実装 | コンテキストと記憶 | 呼び出し時のみ（親とは別コンテキスト） |
| `.claude/commands/*.md` | **スラッシュコマンド**: 定型プロンプトのパッケージ。Spec-kit の `/speckit.*` は、まさにこの仕組みの上に配布されるコマンド集 | ツールオーケストレーション | 呼び出し時のみ |
| `.mcp.json` | **MCP サーバー**接続定義: 外部ツール（DB、チケット管理、社内 API 等）をエージェントの手足として追加する | ツールオーケストレーション | ツール定義として常駐（増やしすぎはコンテキスト税、§9.1） |
| `settings.json` の permissions | 許可・禁止する操作の宣言（実行してよいコマンド、触ってよいパス） | ガードレール | コンテキスト外（強制力を持つ） |

押さえるべき要点は 3 つです。

- **常駐か都度かの区別がここでも効く**: CLAUDE.md / AGENTS.md に何でも書き足すのは constitution の肥大化（§10.4）と同じアンチパターンで、都度で足りる知識は Skills に逃がすのが定石です
- **hooks だけは性質が違う**: 他のファイルが「エージェントに読ませる情報」なのに対し、hooks と permissions は**エージェントの外側で必ず実行される強制力**です。「テストを必ず回す」を LLM への指示（守られないことがある）ではなく hooks（必ず実行される）で実現するのが、ハーネスエンジニアリングの要点です。Kiro の Agent Hooks（§8.1）も同じ思想の IDE 内実装です
- **Spec-kit 自体がハーネス成果物**: `specify init` が配置する `.specify/`（テンプレート・スクリプト）と `/speckit.*` コマンド群は、「SDD の規律」をコマンド・テンプレートとしてパッケージしたハーネスそのものです。§9.3 で「SDD はコンテキストエンジニアリングの制度化」と述べましたが、より広くは「**SDD ツールとは、仕様を中心に据えたハーネスの既製品**」と言えます

### 11.4 SDD 導入チームにとっての含意

- Spec-kit / Kiro を導入した時点で、チームは既にハーネスエンジニアリングを始めています。次の一手は、SDD がカバーしない層——特に **hooks による決定論的な品質ゲート**（テスト・lint の強制）と **permissions によるガードレール**——を足すことです。§6.3 の「テストが常に回る前提」は、指示ではなく hooks で作るのが確実です
- 逆に、ハーネス（CLAUDE.md、Skills、hooks）が既に整っているチームにとって、SDD の導入は「ハーネスに仕様レイヤーを追加する」増分に過ぎず、導入コスト（§12）は見かけより小さくなります
- 失敗のたびに「プロンプトを直す」のではなく「constitution / Skills / hooks のどれを直すべきか」を問う習慣が、§11.1 の中核原則のチーム実装です

## 12. 導入しない場合との比較 — メリット・デメリット

最後に、Spec-kit / Kiro を「導入するか、しないか」の意思決定に使える形で、使わない場合との得失を整理します。

### 10.1 比較の前提: 「使わない」には 2 つのベースラインがある

- **(A) 素の AI コーディング**: Claude Code / Copilot に直接指示して進める現在の主流スタイル（vibe coding を含む）。仕様に相当するものはチャットログにしか残らない
- **(B) ツールなしの自前 SDD**: 専用ツールは入れず、CLAUDE.md や手書きの Markdown 仕様書で SDD の規律だけを運用で実践するスタイル

(A) との比較は「SDD をやるか」の判断、(B) との比較は「SDD をツールでやるか」の判断であり、論点が異なります。

### 10.2 (A) 素の AI コーディングと比べた場合

| 観点 | ツールあり（SDD） | ツールなし（素の AI コーディング） |
|---|---|---|
| 初速 | ✗ 遅い（仕様→計画→タスクの往復が先行） | ◎ 速い（すぐコードが出る） |
| 大規模・複数セッションのタスク | ◎ 意図がファイルで維持される | ✗ コンテキストロットでドリフト（§9.1） |
| 意図の永続性・引き継ぎ | ◎ 仕様がリポジトリに残る | ✗ チャットログとともに揮発 |
| レビュー可能性 | ◎ 仕様の段階でレビューできる | △ 生成コードの差分から意図を逆算 |
| チーム展開・再現性 | ◎ constitution とテンプレートで標準化 | ✗ 個人のプロンプト力に依存 |
| トークン・時間コスト | ✗ 多い（全フェーズが LLM 呼び出し） | ◎ 少ない |
| 学習・追随コスト | ✗ ツールの習得＋破壊的変更への追随（§4.1） | ◎ 不要 |

**メリット（導入で得るもの）**

- 意図がレビュー可能・永続的な成果物になり、担当者・セッション・エージェントを跨いで引き継げる（§2）
- コンテキストロット対策（外部メモリ化、タスク分割）が個人の工夫ではなく**構造として**組み込まれる（§9.3）
- 暗黙知が constitution として明文化され、品質が個人のプロンプト力に依存しなくなる
- 失敗したとき「仕様が悪かったのか、実装が悪かったのか」を切り分けられる（素の AI コーディングでは切り分け不能）

**デメリット（導入で失うもの）**

- 初速。1 行目のコードが出るまでの時間は確実に伸びる。小さなタスクではこのオーバーヘッドが本体を上回る（§4.2）
- トークン消費と待ち時間。仕様生成・明確化・計画・検証のすべてが LLM 呼び出しになる
- プロセスに従う規律の維持コスト。レビューを省略し始めると「工程だけ重い vibe coding」に退化する（§5、§8.3 の Classmethod 実例）
- ツール自体の学習コストと、速いリリースサイクルへの追随コスト（v0.10 の破壊的変更のような事態は今後も起こりうる）

### 10.3 (B) 自前の SDD 運用と比べた場合

SDD の価値の源泉は規律であってツールではないため、「Markdown 仕様書＋CLAUDE.md で自前運用する」のは十分成立する選択肢です。そのうえでツールが上乗せするものと、自前に残る利点は次の通りです。

**ツール導入のメリット**

- テンプレート・フェーズゲート・整合性検証（`/speckit.analyze`）・チェックリストが**既製で**付いてくる。自前運用ではこれらが各人の自制心に依存し、レビュー品質と仕様の構造が人によってばらつく
- チーム・プロジェクト間で仕様の置き場所と構造が標準化され、他チームの仕様も同じ読み方ができる
- コミュニティの改善（テンプレートの洗練、新エージェント対応）に自動的に乗れる

**自前運用に残るメリット**

- ワークフローを自分たちのプロセスに 100% 合わせられる（Spec-kit のフェーズ構成やテンプレートは思想が固定的で、合わない部分のカスタマイズには手間がかかる）
- ツールの仕様変更・破壊的変更への追随が不要で、学習対象も増えない
- 依存を増やさない（生成物も運用もただの Markdown と Git のまま）

実務的には、**自前 Markdown 運用で SDD の規律を先に定着させ、手作業の限界（整合性チェックの漏れ、仕様構造のばらつき）を感じた時点でツールを導入する**のも正当なルートです。この順序なら、ツールは「規律の代替」ではなく「定着した規律の省力化」として機能します。

### 10.4 判断の目安

**導入のメリットが上回る条件**

- 複数人・複数セッションを跨ぐ、ある程度の規模の開発が定常的にある
- 引き継ぎ・監査・レビューの証跡として「なぜこう作ったか」を残す必要がある
- 仕様レビューの時間をプロセスとして確保する合意がチームにある

**見送り（または自前運用）が合理的な条件**

- 開発の大半が小さな修正・単発のスクリプトで、§4.2 のオーバーヘッドが常に本体を上回る
- 一人開発で引き継ぎがなく、コンテキストは CLAUDE.md で足りている
- まだ仕様レビューの文化がなく、先に (B) で規律だけ作る方が定着しやすい

いずれの場合も、判断の本質は §8.3 の結論と同じです: **ツールは規律を省力化するが、代替はしない**。導入とは「初速とトークンコストを支払って、意図の永続性・再現性・レビュー可能性を買う」投資であり、支払いに見合う規模と体制があるかが判断基準になります。

## 13. まとめと社内での始め方

- SDD は「プロンプトの使い捨て」をやめ、意図をレビュー可能・永続的な成果物に昇格させる方法論。Spec-kit はその GitHub 製リファレンス実装
- 効果が出るのは、要件が多く規模のあるタスク × テストが回る環境 × 仕様レビューをやる意思のあるチーム。小さな修正には使わない
- 運用の目標は **spec-anchored**（振る舞いの変更は仕様から、仕様と実装は同一 PR、受け入れ基準はテストに接続）
- 粒度の指針は「**仕様は判定可能性で切り、タスクはコンテキスト容量で切る**」。spec に How を書かない規律がドリフト防止の最重要ポイント
- ファイル構成は「**読み込まれ方（常駐・都度・使い捨て）で層別し、層ごとに寿命とトークン予算を決める**」L0〜L3 の 4 層が基本形（§10）
- 変更は「**既存の受け入れ基準を書き換えるか**」で新 spec / 修正を判断（§6.5）。バグは「仕様のどこに違反したか」で**実装バグ・仕様バグ・仕様の欠落**に3分類し、spec を触るかを決める（§6.6）
- 視野を広げれば SDD は**ハーネスエンジニアリングの一形態**（§11）。「失敗したらプロンプトでなく、constitution / Skills / hooks のどれを直すか」を問い、失敗をハーネスの改善に変換し続ける
- ツール選択は、既存エージェント資産があり環境を変えたくないなら **Spec-kit**、GUI での可視化・承認フローと AWS 親和性を取るなら **Kiro**。ただし品質を決めるのはツールでなく仕様レビューの規律
- 原理としての SDD は「**コンテキストエンジニアリングのファイル規約・プロセスへの制度化**」。constitution が常駐コンテキスト、spec/plan/tasks が外部メモリに対応する
- 導入判断の本質は「**初速とトークンコストを支払って、意図の永続性・再現性・レビュー可能性を買う**」投資かどうか。規模と体制が見合わないなら、自前 Markdown 運用で規律だけ先に作るのも正当（§12）

### 始め方（推奨ステップ）

1. **パイロット 1 機能を選ぶ**: 要件が 5〜10 個程度ある、新規性のある機能が適切。バグ修正は選ばない
2. **constitution をチームで書く**: 30 分のモブ作業で十分。単純さの原則・テスト方針・技術制約を明文化し、レビューして合意する
3. **specify → clarify → plan まで回して一度止まる**: 生成された spec と plan を人間がレビューし、抽象度の混入（spec に技術が書かれていないか）をチェックする
4. **implement 後にふりかえり**: 「仕様に書かなかったせいでエージェントが暴走した箇所」を洗い出し、constitution に還元する
5. バージョンは `specify self check` で確認し、チーム内で揃える。**公式リポジトリ以外の情報は日付を必ず確認する**（v0.10 で CLI が大きく変わったため）
